# МАРСИ-Job — концепция сервиса и план разработки

**Продукт:** Telegram-бот для поиска работы и подбора персонала (РУ-сегмент + международная удалёнка)
**Ядро подбора:** детерминированный математический движок МАРСИ (по документу «МАРСИ-DN1»), LLM — только парсер
**Дата:** 12.11.2026 · **Статус:** концепция на утверждение, разработка после согласования

---

## 1. Суть продукта

Двусторонний матчинг-сервис в Telegram:

- **Кандидат** заполняет профиль (или загружает резюме — его разбирает ИИ-парсер) и получает **ранжированный по формуле МАРСИ** список вакансий от работодателей, с объяснением, почему вакансия подходит и что мешает идеальному матчу.
- **Работодатель** публикует вакансию и ищет кандидатов тем же алгоритмом: получает топ кандидатов с итоговым скором и разбором вклада каждого фактора.

Ключевое отличие от hh.ru / Хабр Карьеры / LinkedIn: не семантический поиск по ключевым словам, а **детерминированное математическое ядро**, которое:
1. раскладывает «найти работу» и «найти сотрудника» на атомарные факторы (ячейки МАРСИ);
2. считает вес и критичность каждого фактора (формулы состояния);
3. учитывает **синергии и конфликты** между факторами (Φ-матрица «Клея»);
4. вычитает **ресурсозатраты** на сближение пары (релокация, обучение, онбординг);
5. поглощает неизвестное коэффициентом энтропии ε и **объясняет** результат (зона валентности — первопричина несовпадения).

Учитывается максимум переменных: от хард-скиллов до нейроотличий и психо-эмоционального профиля — не для дискриминации, а для подбора **комфортной среды**, где человек реально приживётся (см. раздел 6 — правовые ограждения).

## 2. Ядро МАРСИ (краткая выжимка из документа)

МАРСИ = **Метод Атомарного Разделения и Сопоставления Информации**. Принцип как в микросервисах/ECS: монолит-проблема декомпозируется до атомарных ячеек, каждой ячейке назначается микро-метод (решение) из базы, затем решения «склеиваются» в единый протокол.

### 2.1. Формулы документа

**Статическая формула состояния ячейки** (p. 3):

```
A_n(i+1) = (C_n^t + D_n^m + E_n^f + F_n^e + G_n^y + H_n^g + I_n^h) · r_obj^A_n + ε
```

**Взвешенный вид** (p. 11, Q&A) — рабочий вариант для реализации:

```
A_n(i+1) = Σ_p (w_p^C · C_n^p) · R_obj^A_n + ε,
p ∈ {t, m, f, e, y, g, h}
```

**Вес ячейки** (p. 7):

```
W_{i+1}^A_n = (A_n^(t·w) + A_n^(m·w) + A_n^(f·w) + A_n^(e·w) + A_n^(y·w) + A_n^(g·w) + A_n^(h·w)) + ε
```

**Итоговый «Клей»** (p. 6):

```
КЛЕЙ_итоговый = Σ W_i − Σ r_i + Σ Φ_jk − ε
```

**Приоритет связки «проблема → решение»** (p. 4):

```
B_{O_n}^{A_n} = (A_n / V) · R · (O_n / (A_n − Z_n)),   если (A_n − Z_n) = 0 → +1
```

**Коэффициент перекрёстного взаимодействия** (p. 7): Φ_jk приводится логарифмом к шкале (0;1):

```
Φ_jk^{A_n^n} × Φ_jk^{A_n^1} = log_{Φ...}((t + m + …)_1 + (t + m + …)_2 + …)
```

**Семантика Φ_jk** (жёстко прописывается в коде):
- `Φ > 0` — синергия (пара усиливает матч, алгоритм отдаёт ей предпочтение);
- `Φ = 0` — нейтральность;
- `Φ < 0` — конфликт (штраф склейке);
- `Φ = −∞` — **абсолютное противопоказание** (паре запрещено быть в выдаче рядом: например, вакансия требует релокации, а кандидат не может переехать).

### 2.2. Переменные

| Переменная | Смысл в МАРСИ |
|---|---|
| t | время (срочность) |
| m | контекст пространства |
| f | факты реальности |
| e | сознательная цель |
| y | критичность ущерба |
| g | достоверность/уверенность в данных |
| h | ценность решения / ROI |
| r | ресурсозатраты (энергия/бюджет) |
| ε | коэффициент энтропии (шум, неизвестное) |
| w | весовые коэффициенты параметров |
| V | монолит — исходная проблема |
| A_n | атомарная ячейка (микро-задача) |
| O_n | микро-метод (решение из БД) |
| S | симптом (наблюдаемый признак) |
| Z_n | первопричина (зона валентности) |
| Φ_jk | перекрёстное взаимодействие ячеек |

### 2.3. Пайплайн из документа (5 шагов)

1. **Сбор данных (парсинг):** текст → нормализованные числа 0.0–1.0 (LLM работает *только* здесь, как парсер в JSON).
2. **Вычисление состояний:** прогон через формулу с учётом r и ε.
3. **Построение графа:** карта связей, приоритет P, корневая проблема (зона валентности).
4. **Семантическое сопоставление:** подбор микро-методов из БД (вектора + косинусное сходство / евклидово расстояние, логарифм для выравнивания шкал).
5. **Склейка плана:** единый протокол, приоритет узлам с максимальным весом.

Без LLM система работает полноценно — через пошаговое анкетирование (детерминированный путь, «без галлюцинаций»). Именно так строим MVP: анкета — основной ввод, LLM-парсер резюме — удобное дополнение.

## 3. Перенос МАРСИ на подбор персонала

### 3.1. Словарь соответствий (HR-адаптер)

Доменный адаптер из документа («ярлыки на входе меняются, логика — нет»):

| Сущность МАРСИ | В МАРСИ-Job |
|---|---|
| V (монолит) | «Найти лучшую работу» (кандидат) / «Закрыть вакансию лучшим кандидатом» (работодатель) |
| A_n (ячейка) | Атомарный **фактор соответствия**: навык, локация, формат работы, график, зарплата, стиль коммуникации, сенсорная нагрузка и т.д. |
| Микро-задачи C…I | Конкретные требования вакансии / свойства кандидата внутри фактора |
| O_n (микро-метод) | **Вакансия** (решение для кандидата) / **кандидат** (решение для работодателя) |
| S (симптом) | Наблюдаемое: «не зовут на интервью», «отклоняют на скилл-скрининге», «вакансия висит месяц» |
| Z_n (зона валентности) | **Первоопричина несовпадения** и что изменить, чтобы матч стал возможен |

### 3.2. Семантика параметров в HR-домене

| Параметр | У кандидата | У работодателя/вакансии |
|---|---|---|
| **t** — время | Срочность трудоустройства (мес. до дохода 0, риск простоя) | Срочность закрытия вакансии (стоимость простоя ставки) |
| **m** — пространство | Город, ЧП, готовность к релокации/гибриду | Локация офиса, допустимые ЧП, релокационный пакет |
| **f** — факты | Проверяемое: опыт, образование, сертификаты, портфолио, языки | Проверяемое: стадия компании, бренд, отзывы, юр. данные |
| **e** — цель | Карьерная траектория, миссия, чего хочет достичь | Наймовая цель: какую задачу закрывает роль |
| **y** — критичность | Цена промаха для кандидата (месяцы поиска, финансовая подушка) | Цена плохого найма (простой, стоимость замены, риск проекта) |
| **g** — достоверность | Верификация профиля: подтверждённые скиллы vs задекларированные | Заполненность и честность вакансии, реакция на отклики |
| **h** — ROI | Ожидаемая ценность: зарплата, рост, стабильность, обучение | Ожидаемая продуктивность, срок выхода на окупаемость |
| **r** — ресурсы | Затраты на сближение: переезд, обучение, снижение зарплатных ожиданий, онбординг | Затраты: онбординг, обучение, релокационный пакет, время интервьюеров |
| **ε** — энтропия | Незадекларированные факторы, «чёрные ящики» профиля | Скрытые условия, текучка, реальная культура |

### 3.3. Скоринг пары «кандидат × вакансия»

Для каждой пары:

1. **Разложение на факторы** — фиксированный словарь HR-адаптера (раздел 4), у каждого фактора нормализованные значения 0.0–1.0 с обеих сторон.
2. **Вес каждого фактора** — взвешенная формула состояния:

```
W(A_n) = Σ_p (w_p · value_p) · R_obj + ε_n        — важность фактора в данном матче
Match(A_n) = близость(value_кандидат, value_вакансия) · W(A_n)   — вклад фактора в скор
```

3. **Синергии и конфликты** Φ_jk — матрица взаимодействий пар факторов (примеры ниже).
4. **Ресурсозатраты** r_i — сумма затрат на сближение (релокация, ап-скилл-путь, онбординг).
5. **Итоговый скор пары:**

```
SCORE(кандидат, вакансия) = Σ Match_i − Σ r_i + Σ Φ_jk − ε_общий
```

6. **Абсолютные противопоказания (Φ = −∞):** юридические запреты (нет права работать в юрисдикции), недоступная локация без релокации, недопустимый график, зарплатные вилки не пересекаются, вакансия требует навыка из «критического» списка, которого нет. Пара не попадает в выдачу (или попадает с пометкой «требуется сближение» и списком, что именно поменять).

Примеры Φ:
- **Синергия:** «аутистический спектр + глубокая специализация в анализе данных + тихий офис/удалёнка» → Φ > 0; «СДВГ + разнообразные короткие задачи + гибкий график» → Φ > 0; «опыт в геймдеве + вакансия геймдев» с пересекающимся стеком → Φ > 0.
- **Конфликт:** «высокая тревожность + open-space + холодные звонки» → Φ < 0; «режим многозадачности у работодателя + монозадачный профиль кандидата» → Φ < 0.
- **Противопоказание:** «требуется ночная смена + кандидат не может по здоровью» → Φ = −∞.

### 3.4. Итеративный цикл (динамика, i → i+1)

Шаг итерации = отклик/отказ/лайк/дислайк (по документу: «выполнил микро-метод + дал обратную связь»):
- отклик без ответа работодателя → +ε вакансии (шум/недостоверность), падает индекс доверия вакансии;
- отказ по навыку → вес фактора навыков у кандидата ↑ (критичнее), зона валентности указывает на пробел;
- дислайк кандидатом «не мой формат» → калибровка весов факторов формата у этого кандидата;
- систематически успешные (высокий W при адекватном r) вакансии/кандидаты получают **индекс доверия** выше (внутренний рейтинг из документа).

Условие остановки цикла по каждой паре (защита от бесконечных циклов, п. 5 документа): лимит итераций + порог «допустимой нормы» скоринга.

### 3.5. Зона валентности — объяснимость

Каждой стороне бот объясняет:
- **кандидату:** «Топ-1 вакансия набрала 0.82: +0.31 стек совпадает, +0.18 формат удалёнки, +0.12 зарплатная вилка, −0.07 требуется+1 навык (обучение ~1 мес), Φ-бонус +0.09: твоя специализация и их стек задач усиливают друг друга. Ближайшая альтернатива 0.74, почему ниже: …»;
- **и главное** — «почему тебя в целом редко зовут»: граф факторов ранжирует первопричину (например: g-пробел — навыки задекларированы, но не подтверждены; не хватает фактора f — нет публичного портфолио). Это применение «интервенции»: обнуление какого фактора максимально поднимает суммарный скор — тот и корень.

## 4. Факторная модель (полный список переменных)

Продолжение и структурирование списка из брифа. Каждый фактор — ячейка A_n: нормализуется в 0.0–1.0, имеет вес w (калибруется), участвует в Φ-матрице.

**A. Профессиональные (hard)**
1. Хард-скиллы по доменам (уровень 0–1 + подтверждённость g: тест/портфолио/референс)
2. Стек инструментов и глубина владения
3. Опыт: годы, релевантность, глубина специализации vs широта
4. Отраслевой опыт (финтех, геймдев, промышленность…)
5. Образование, сертификаты, лицензии
6. Портфолио/публичные работы (GitHub, кейсы)
7. Языки: русский, английский (уровни), другие
8. Управленческий опыт (люди, бюджеты, проекты)

**B. Soft-скиллы и коммуникация**
9. Коммуникация: письменная/устная, язык общения
10. Работа в команде / автономность
11. Переговоры, презентации, публичность роли
12. Менторство, онбординг коллег
13. Конфликт-менеджмент, обратная связь
14. Клиентоориентированность (B2B/B2C-контакт)

**C. Формат и условия занятости**
15. Формат: офис / гибрид / удалёнка / релокация
16. График: полный день, сменный, ночной, гибкие часы, 4/2, 2/2
17. Тип договора: ТК РФ, ГПХ, самозанятый, ИП, contractor (междунар.)
18. Зарплатные ожидания: вилка, периодичность, валюта, бонусная часть
19. Командировки: допустимый %
20. Оформление для международной удалёнки (инвойсинг, EOR, B2B-контракты)

**D. Локация (m)**
21. Город/часовой пояс
22. Радиус commute / допустимое время в дороге
23. Готовность к релокации: города/страны, сроки
24. Право работать: гражданство, ВНЖ, разрешения, визовая поддержка
25. Транспортная доступность офиса

**E. Психо-эмоциональный профиль**
26. Стрессоустойчивость, работа с дедлайнами
27. Тревожность (в т.ч. социальная), потребность в предсказуемости
28. Уровень выгорания / восстановления
29. Многозадачность vs монозадачность
30. Темп работы, отношение к переключениям контекста
31. Отношение к micromanagement / самостоятельность
32. Предпочтительный размер команды и тип коммуникации (синхрон/асинхрон)
33. Мотивация: достижения, деньги, миссия, признание, стабильность, развитие
34. Отношение к риску (стартап-волатильность vs корпоративная стабильность)

**F. Когнитивный профиль и нейроотличия**
35. СДВГ-профиль (внимание, hyperfocus, потребность в дедлайновой структуре)
36. Аутистический спектр (сенсорная чувствительность, потребность в чётких инструкциях)
37. Дислексия/дисграфия, особенности обработки текста
38. Стиль обучения (визуальный/практический/теоретический)
39. Скорость входа в новую область, обучаемость

**G. Личностные и ценностные**
40. Интроверсия/экстраверсия рабочей роли
41. Интересы и хобби (культурный fit)
42. Ценности: этика, миссия продукта, ESG, открытый код
43. Культура компании: формальная/неформальная, иерархия/флэт
44. Отношение к корпоративным активностям
45. Стадия компании: стартап / масштабирование / корпорация / госсектор

**H. Физические и медицинские (только добровольно, особая категория ПДн)**
46. Ограничения по здоровью, влияющие на условия (физическая нагрузка, сенсорика, освещение)
47. Потребность в инклюзивной среде (доступность офиса, ergonomics)
48. Требования вакансий к физике (поднятие тяжестей, стоячая работа, зрение/слух)

**I. Социально-демографические (только с явного согласия, не фильтры для работодателя)**
49. Возрастная группа (для возраст-дружественного скоринга и юридической защиты, не для отсечения)
50. Семейный статус, дети/иждивенцы (влияет на график/релокацию)
51. Беременность/планы (защищается законом, только для подбора комфортных условий)
52. Воинский учёт (актуально для РУ-сегмента: бронь, ограничения релокации)

**J. Карьерные цели (e)**
53. Траектория: рост вглубь/вширину/в менеджмент
54. Смена профессии, стажировки, re-entry после перерыва
55. Желаемый срок в компании
56. Обучение за счёт работодателя, менторская поддержка
57. Перерывы в карьере и их причины (уход, здоровье, релокация) — учитываются бережно

**K. Контекст поиска (t, y)**
58. Срочность поиска, текущий статус занятости
59. Финансовая подушка (влияет на y — цену промаха)
60. Параллельные офферы, конкурирующие сроки

Каждая группа = кластер ячеек в графе; факторы могут иметь несколько принадлежностей (мульти-зависимость по документу).

## 5. Сценарии работы

### 5.1. Кандидат
1. `/start` → выбор роли → онбординг-анкета (детерминированный путь: 25–35 вопросов с нормализованными ответами; разделы E/F/G/H помечены «опционально, повышает точность»).
2. Альтернатива: прислать резюме текстом/файлом → LLM-парсер строит тот же JSON-профиль → кандидат подтверждает/правит каждое поле (LLM только предлагает, человек утверждает).
3. `/match` → топ-N вакансий: скор, разбор вклада факторов, Φ-бонусы, что сблизить для +X очков.
4. Отклик в 1 клик (бот передаёт контакт работодателю), лайк/дислайк → шаг итерации i→i+1, веса пересчитываются.
5. `/why` — зона валентности: главная причина слабого матча-потока и конкретные шаги (какой навык подтянуть, какое поле профиля дополнить).

### 5.2. Работодатель
1. Регистрация (профиль компании: стадия, культура, скорость ответа — влияет на g).
2. Публикация вакансии: структурированная форма по той же факторной модели (зеркальная анкете кандидата).
3. `/search` → топ кандидатов по КЛЕЮ с разбором: совпадения, синергии, риски (r), пробелы.
4. Приглашение кандидату в 1 клик; статистика по вакансии (просмотры, скор-распределение).

### 5.3. Админ
Модерация вакансий (запрет дискриминационных формулировок — автопроверка + ручная), калибровка весов w, просмотр тест-кейсов.

## 6. Этика и право (встроено в алгоритм, не поверх)

1. **ТК РФ, ст. 64** — запрет дискриминации по полу, возрасту и др. → пол/возраст/семейный статус **недоступны работодателю как фильтры и как поля кандидата**. Они участвуют только в sided-скоринге самого кандидата (комфорт среды) и в статистике сервиса.
2. **Особые категории ПДн (152-ФЗ, ст. 10):** здоровье, нейроотличия — отдельное явное согласие, шифрование, хранение обособленно. Работодатель видит агрегированный «индекс совместимости среды» (0–1) без раскрытия диагнозов; кандидат сам решает, раскрывать ли детали.
3. **Международная удалёнка:** принципы GDPR-типа (минимизация, право на удаление) по умолчанию для всех.
4. **Прозрачность:** пользователь видит, какие факторы и с какими весами повлияли на скор (explainability по построению — из формулы).
5. **Право на забвение:** команда удаления профиля стирает все ПДн, включая вектора.

## 7. Архитектура MVP

```
Telegram (aiogram 3) ──► Bot App (Python 3.11+)
                            │
                            ├─► marsi-core (чистый модуль, без I/O):
                            │     · normalize.py    — приведение факторов к 0..1 (log-шкалы)
                            │     · factors.py      — HR-словарь (доменный адаптер)
                            │     · weights.py      — w, Φ-матрица, r-модель, ε
                            │     · engine.py       — формулы W / Match / КЛЕЙ / зона валентности
                            │     · graph.py        — связи факторов, приоритет P
                            │
                            ├─► parser-llm (адаптер OpenAI-compatible): резюме → JSON-профиль
                            │     (строгая схема, валидация, fallback на анкету)
                            │
                            ├─► storage (SQLite для MVP → PostgreSQL при росте)
                            │     users / profiles / vacancies / matches / feedback
                            │
                            └─► vector layer (embeddings факторов, косинус) — этап 2
```

Принципы: ядро — чистые функции (легко тестировать и калибровать по разделу 10 документа); бот — тонкая обвязка; LLM изолирован за интерфейсом парсера (можно отключить — система полностью работоспособна на анкетах).

| # | Этап | Содержание | Критерий готовности |
|---|---|---|---|
| 0 | Спецификация HR-адаптера | Словарь факторов (раздел 4) в машиночитаемом виде, веса w, матрица Φ (синергии/конфликты/противопоказания), модель r и ε, 5 тест-кейсов «идеальный матч» из документа (p. 10), схема БД | SPEC согласована, тест-кейсы зафиксированы с эталонными ответами |

| 2 | Бот: кандидат (детерминированный путь) | Анкета, профиль в БД, `/match`, выдача топ-N со скором и объяснением | Сценарный тест анкеты → матчинга на seed-вакансиях |

| 5 | Итеративный цикл | Отклики/дислайки/отказы → пересчёт весов, индекс доверия, остановка цикла | Тест: серия фидбеков меняет ранжирование предсказуемо |

**Оценка:** этапы 0–1 (ядро) — основа качества, ~40% времени; 2–4 — функциональный MVP; 5–7 — производство. Векторный слой (embeddings) и внешние интеграции (API джоб-борд для seed-наполнения) — пост-MVP: MVP живёт на вакансиях, публикуемых работодателями напрямую + демо-набор.

**Что понадобится от вас по ходу:**
- токен бота от @BotFather (на этапе 2, для локальных тестов);
- ключ LLM-провайдера, которого вы предпочитаете (на этапе 3; можно отложить — анкета самодостаточна);
- решение по хостингу на этапе 7 (VPS / Railway / ваш сервер).

## 9. Метрики MVP (по разделу 10 документа)

- **Бенчмарк-конкурент:** поиск hh.ru (релевантность выдачи) — сравниваем точность топ-10 на одинаковых профилях.
- **Целевая метрика:** время до релевантного матча (у hh — дни откликов, у нас — минуты скоринга) и точность топ-10 против эталона тест-кейсов ≥ 80%.
- **5 тест-кейсов** с задокументированными «идеальными» ответами (джун-разработчик с СДВГ → удалёнка с гибким графиком; сеньор с релокацией; смена профессии; мама в декрете → частичная занятость; нейроатипичный аналитик → тихая среда). На них калибруются веса w.

## 10. Монетизация (модели из документа, адаптированные)

## 11. Риски и решения

| Риск | Решение |
|---|---|
| Дискриминационное использование чувствительных факторов | Жёсткие ограничения архитектуры (раздел 6): фильтров по полу/возрасту нет, особые категории — только с согласия и в агрегированном виде |
| «Холодный старт» — нет вакансий | Демо-набор + ручной посев; интеграция с API джоб-бордов пост-MVP |
| Субъективность самооценок (E/F/G-факторы) | Коэффициент g: самооценки весят меньше подтверждённых фактов; калибровка вопросами-ситуациями |
| Переусложнение формулы | MVP на взвешенной статической формуле; динамическая (фрактальная) — поэтапно, после проверки статической на тест-кейсах |
| LLM-галлюцинации парсера | LLM только парсит в строгую схему, каждое поле подтверждает пользователь; ядро полностью детерминировано |
