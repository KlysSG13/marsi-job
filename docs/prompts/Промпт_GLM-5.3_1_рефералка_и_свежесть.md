## 1. Реферальная программа

### 1.1. Механика

- Каждый пользователь получает персональную реферальную ссылку `https://t.me/<bot_username>?start=ref_<CODE>` (aiogram 3: payload в `CommandStart`).
- CODE — 8 символов `[a-z0-9]`, генерируется один раз при первом обращении к `/referral`, хранится у пользователя.
- Новый пользователь по ссылке: фиксируется связка рефerrer→referred в момент первого `/start`.
- **Награда выдаётся не за старт, а за завершённый онбординг** (анкета заполнена, профиль создан): обоим по **7 дней Plus** (прибавка к `active_until`; если Plus не активен — активируется от сегодня).
- Уведомление рефerrerу: «По твоей ссылке присоединился друг — вам обоим +7 дней Plus».

### 1.2. Анти-абьюз (жёсткие правила)

1. Реферал = аккаунт, впервые увиденный системой (нет профиля и истории). Уже существовавший пользователь по ссылке → приветствие без начислений.
2. Нельзя привести себя (свой код в своём аккаунте игнорируется).
3. У пользователя **один рефerrer навсегда** (повторные ссылки не меняют привязку).
4. Лимит начислений рефerrerу: **5 в календарный месяц** (config). Сверх лимита: награду получает только новичок, рефerrerу — сообщение «лимит в этом месяце исчерпан».
5. Награда за одного referred — ровно один раз.

### 1.3. Интерфейс

- `/referral` — карточка: твоя ссылка, кнопка «Поделиться» (share-ссылка `tg://msg_url?url=...` или `switch_inline_query`), счётчики: приглашено / дней заработано / лимит месяца.
- В `/balance` — блок «Рефералы» одной строкой.
- Админ: `/refstats` — всего рефералов, топ-10 рефerrerов, конверсия старт→онбординг.

### 1.4. Конфиг (добавить в `data/pricing.json`)

```json
"referral": {
  "reward_days_plus": 7,
  "max_credits_per_month": 5,
  "reward_on": "onboarding_complete",
  "code_length": 8
}
```

### 1.5. БД

- `referral_codes(tg_id UNIQUE, code UNIQUE, created_at)`.
- `referrals(referrer_tg_id, referred_tg_id UNIQUE, created_at, status pending/credited, credited_at)`.
- Начисление дней Plus — через существующую механику подписок (добавить дни), отдельной таблицы наград не заводить.

## 2. Свежесть вакансий

В базе ~6 600 вакансий (включая импортированные); без управления свежестью доверие к выдаче падает.

### 2.1. Механика

- Каждая вакансия получает статус свежести по `updated_at` (или `created_at`, если обновлений не было):
  - `< 7 дней` — метка «🆕 свежая»;
  - `7–30 дней` — без метки;
  - `> 30 дней` — «⚠ не обновлялась N дней»;
  - `> 45 дней` — **авто-архивация** (уходит из `/match`, не удаляется; работодатель может реактивировать, для бесплатной вакансии реактивация возможна 1 раз/30 дней).
- `updated_at` обновляется при любой правке вакансии работодателем и при реактивации.
- **Дедупликация импортированных**: одинаковые (название + работодатель + город) — оставлять последнюю по дате, остальные архивировать. Запуск — разовая миграция + проверка при новых импортах.
- В `/match` вакансии старше 30 дней не показываются, **кроме случая**: если после фильтра осталось < 3 матчей — показать более старые с пометкой «давно не обновлялась» (fallback, не оставлять кандидата с пустой выдачей).
- Порядок в выдаче не менять (только скор-порядок МАРСИ) — свежесть фильтрует и маркирует, но **не пересортировывает** и не влияет на скор.
- Уведомление работодателю: за 7 дней до авто-архивации его вакансии (при первом взаимодействии в сутки, best-effort — как напоминания подписок): «Вакансия "X" уйдёт в архив N-го. Обновить → /myvacancies».

### 2.2. Интерфейс и админ

- В карточке вакансии — строка «Обновлено: N дн. назад».
- `/myvacancies` для работодателя: список его вакансий со статусом (активна / архив / дней до архива), кнопки «Обновить», «Реактивировать».
- Админ: `/vacstats` — всего/активных/архив, распределение по свежести (0–7/8–30/31–45/>45), сколько задублировано и архивировано миграцией.

### 2.3. Конфиг

```json
"freshness": {
  "fresh_days": 7,
  "stale_days": 30,
  "auto_archive_days": 45,
  "min_fallback_results": 3,
  "reactivate_cooldown_days": 30
}
```

## 3. Чего НЕ делать

1. Не трогай ядро: `engine.py`, `valence.py`, `factors.json`, `phi_rules.json`, `calibration.json` — только чтение.
2. Свежесть и рефералка не влияют на скор и порядок выдачи (нельзя «продавать свежесть»).
3. Не ломай существующие команды и 210 тестов — обновляй и добавляй.
4. Миграции — назад совместимые, без потери боевых данных; боепроводность: сначала тесты, потом деплой.
5. Никаких рассылок «всем сразу» — только упомянутые точечные уведомления.
