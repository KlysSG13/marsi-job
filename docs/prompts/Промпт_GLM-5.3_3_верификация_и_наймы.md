## 1. Верификация навыков (подтверждение g-фактора)

### 1.1. Суть

Кандидат проходит короткий квиз по навыку в боте → навык получает статус «✓ подтверждён» → его g-фактор в профиле растёт → работодатель в `/search` видит бейджи и может фильтровать по подтверждённости. Для кандидата — бесплатно (это качество базы, а не платная стена).

### 1.2. Банки вопросов

- Каталог: `data/verification/skills/<skill_id>.json` — по каждому навыку 15–25 вопросов (формат: текст вопроса, 4 варианта, индекс верного, 1-строчное пояснение для финального отчёта, тег подтемы).
- Стартовый набор (7 навыков, содержание — заглушки-примеры, админ заменит на реальные): `python`, `sql`, `javascript`, `git`, `excel`, `linux`, `testing`. Каждому навыку — человекочитаемое название и привязка к фактору/скиллу из факторной модели профиля (маппинг `skill_id → factor/skill key` в `data/verification/mapping.json`).
- Вопросы выбираются случайно (seed сессии), порядок вариантов перемешивается.

### 1.3. Механика квиза

- `/verify` → список доступных навыков (с отметками: не проверен / подтверждён N-го / провален, повтор через N дней) → старт.
- **8 вопросов** из банка, по одному с кнопками вариантов; таймер **10 минут** на попытку (просрочено → попытка не засчитана, но не считается провальной).
- Порог: **≥ 75%** верных → навык подтверждён; иначе — провал.
- Анти-абьюз лайт (честно документируем в /terms и текстах: «верификация — базовый фильтр честности, не прокторинг»): перемешивание вопросов и вариантов по seed; после попытки **не показывать** верные ответы; cooldown после провала — **7 дней**; попытки не ограничены по числу, только cooldown.
- Подтверждение действует **730 дней**, потом бейдж гаснет («истёк срок»).

### 1.4. Интеграция g-фактора (критично: ядро не трогать)

- Посмотри, как факторная модель хранит подтверждённость (в концепции: «уровень 0–1 + подтверждённость g»). Внеси изменение **на уровне данных профиля**: квиз ставит навыку `verified=true, verified_at, score` → значение g-компоненты этого фактора в профиле повышается по правилу из конфига (например: `g = min(1.0, g_base + 0.3)` при подтверждении).
- **Запрещено** править `engine.py`, `valence.py`, `factors.json`, `phi_rules.json`, `calibration.json`. Если движок не подхватывает g из профиля автоматически — интегрируй через существующий слой `config.py`/профиля, а если это невозможно без правки ядра — остановись и опси ограничение в отчёте, бейджи при этом всё равно работают на выдаче.
- Пересчёт: после подтверждения — пересчитать кэш матчей кандидата (если кэшируется) при следующем `/match`.

### 1.5. Видимость работодателю

- В карточках кандидата из `/search` — бейдж «✓ python (86%)» со датой; в скоринг-отчётах Pro — строка «подтверждённые навыки: …».
- Переключатель в `/search`: «только с подтверждёнными навыками» (бесплатный фильтр по выбранному навыку/набору). Фильтр — на стороне отображения, не влияет на формулу скора.
- Бонус-синергии со свежестью/шеринг-карточками из промпта 1: если есть шаринговая карточка кандидата — добавить в неё строку подтверждённых навыков.

### 1.6. Конфиг и БД

```json

  "questions_per_attempt": 8,
  "pass_score": 0.75,
  "time_limit_min": 10,
  "cooldown_fail_days": 7,
  "valid_days": 730,
```

Таблицы:

- `verified_skills(tg_id, skill_id, score, verified_at, expires_at; UNIQUE(tg_id, skill_id))` — при перепрохождении обновляется на лучший результат.

## 2. Кнопка «Я получил работу» (исходы найма)

### 2.1. Суть

Кандидат сообщает результат поиска → сервис учитывает реальный исход: индекс доверия вакансий/работодателей растёт от фактов, статистика воронки отклик→интервью→найм становится данными (это и есть итеративный цикл МАРСИ из концепции). Взамен — мотивация сообщать честно.

### 2.2. Точки входа

1. Команда `/hired` + пункт в главном меню «🎉 Я вышел на работу».
2. **Лёгкие опросы**: через 14 дней после каждого отклика `/respond` — один раз на отклик, две кнопки: «Пригласили на интервью / Пока нет / Ещё в процессе». Если «пригласили» → веха фиксируется, через 30 дней один повторный: «Оффер?» Да/Нет. Не более 1 опроса в сутки кандидату; тихо, без давления.
3. Ежемесячная ненавязчивая напоминалка активным соискателям (заполнил анкету, ищет работу > 30 дней, не отвечал на опросы): «Как поиск? Есть новости? /hired» — max 1/мес, отключается в настройках.

### 2.3. Сценарий `/hired`

Пошаговый диалог:
1. «Через сервис или в другом месте?» (через сервис → шаг 2; в другом месте → шаг 4).
2. Выбор вакансии из его откликов (если откликов несколько — список; нет откликов → «работодателя не из сервиса», шаг 3).
3. Дата выхода (месяц — достаточно), прошёл ли испытательный срок (да/ещё нет/не дошёл).
4. Если «в другом месте»: одна причина одним выбором — «нашёл быстрее на другой площадке / выше зарплата / не хватало откликов здесь / вакансии не по моему профилю / другое».
5. Финал: поздравление; профиль переводится в статус `employed`: алерты и дайджесты матчей останавливаются, кандидат по умолчанию **скрывается из `/search`** работодателей (в любой момент можно вернуть `/open_to_work`).

### 2.4. Вознаграждение

- Нашёл **через сервис** (есть отклик на эту вакансию) → подарок **30 дней Plus** (один раз в жизни на пользователя; Plus в подарок — для мониторинга рынка, не для активного поиска).
- Нашёл в другом месте → подарок **14 дней Plus** (тоже один раз; мотив дочитать опрос).

### 2.5. Эффекты на данные

- `feedback.py` (это обвязка, не ядро — править можно): успешный найм через вакансию X → +к индексу доверия вакансии X и её работодателю (по существующей шкале; вес события найма выше лайка — заложи коэффициент 3× в конфиг).
- Работодателю в статистике: агрегат «нанято через сервис: N» — показывать только при N ≥ 1, без имён.
- Все исходы — анонимная статистика; в профиле кандидата не публикуется.

### 2.6. Конфиг и БД

```json

  "offer_poll_delay_days": 30,
  "poll_max_per_day": 1,
  "monthly_nudge_days": 30,

```

Таблица `outcome_events(id, tg_id, event_type poll_invite/poll_offer/hired_external/hired_via_service, vacancy_id NULL, employer_id NULL, via_service bool, reason NULL, stage, created_at; UNIQUE-защита от дублей опросов: (tg_id, vacancy_id, event_type))`.
Флаг `user_flags`: `reward_hire_given`, `employment_status(active/employed)`, `outcome_nudges_optin`.

### 2.7. Админ

`/hirestats` — воронка: отклики → интервью (по опросам) → офферы → наймы; сплит через сервис/внешние; топ вакансий по наймам; конверсия отклик→найм.

## 3. Чего НЕ делать

1. Не трогай ядро (`engine.py`, `valence.py`, `factors.json`, `phi_rules.json`, `calibration.json`) — верификация интегрируется данными профиля (см. 1.4), при невозможности — флаг-бейджи без правки ядра и честное описание ограничения.
2. Верификация бесплатна и не влияет на формулу скора напрямую — только через g-компоненту профиля как данные; платного «буста g» не вводить.
3. Фильтр «только проверенные» — отображение, не пересчёт скоров.
4. Никакой публикации личных исходов: только агрегаты (порог N ≥ 1 для работодателя, остальное — админ-статистика).
5. Опросы не навязчивы: лимиты из конфига соблюдаются жёстко, отказ от опроса запоминается (не переспрашивать тот же).
6. Не ломай существующие тесты; миграции назад совместимые.
