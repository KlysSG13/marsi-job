# SPEC — HR-адаптер движка МАРСИ-Job (этап 0)

Версия 0.1 · 12.11.2026 · Источник формул: «МАРСИ-DN1» (разделы 2–4, 6, Q&A)

Спецификация фиксирует доменный адаптер «HR» поверх универсального движка МАРСИ:
словарь факторов (ячейки A_n), параметры (t,m,f,e,y,g,h), веса w, матрицу Φ,
модели ресурсов r и энтропии ε, формулы скоринга, схему БД и 5 эталонных тест-кейсов.
Согласуется с пользователем до начала кодирования ядра (этап 1).

---

## 1. Границы MVP

**Входит:** детерминированный скоринг пары «кандидат × вакансия» по ~33 факторам,
объяснимость (разбор вклада), блокировки (Φ=−∞), зона валентности (первопричина),
итеративный пересчёт по фидбеку, SQLite-хранилище.

**Не входит (пост-MVP):** векторные embeddings, внешние API джоб-бордов,
динамическая фрактальная формула (MVP — взвешенная статическая, p. 11 документа),
группы H (медицина) и I (демография) как отдельные поля анкеты.

**Чувствительные данные:** `neuro_profile`, `sensory_sensitivity`, `structure_need` —
особая категория: заполняются только по явному согласию, работодателю отдаются
исключительно в агрегированном виде (индекс совместимости среды), никогда — как фильтр.

## 2. Словарь факторов (доменный адаптер)

Машиночитаемая версия: `data/factors.json`. Кандидатская сторона = «профиль»,
вакансионная = «требования/условия». Формат значений: JSON-объект по типу фактора.

### 2.1. Типы факторов и функции близости (match: 0..1)

| Тип | Значение кандидата | Значение вакансии | match = |
|---|---|---|---|
| `scalar` | число 0..1 | число 0..1 | `1 − |c − v|` |
| `scalar_stress` | толерантность c | нагрузка v | `c ≥ v ? 1 : max(0, 1 − (v − c)·k)` (k=2) |
| `scalar_inverse` | предпочтение c | нагрузка v | `1 − clamp(c + v − 1, 0, 1)` — чем выше обе, тем хуже |
| `categorical` | множество допустимых | предлагаемое | `v ∈ c ? 1 : 0` |
| `set` | {item: {level 0..1, verified 0..1}} | {item: {req_level, must}} | Σ по общим: min(cand.level/req, 1)·(0.6 + 0.4·verified); must-навык с уровнем < 80% требуемого → блокировка |
| `range_overlap` | [min, max] | [min, max] | длина пересечения / длина меньшего диапазона; нет пересечения → 0 + ресурсная цена |
| `tags` | теги | теги | |∩| / |вакансионные| |
| `duration` | годы (log-норм.) | минимум лет | `cand ≥ req ? 1 : max(0, 1 − (req − cand)/req)` |

Нормализация неоднородных величин (зарплата, минуты, годы) — логарифмическая
(`x_norm = log(1 + x) / log(1 + x_max)`), по документу (p. 8): «сплющить выбросы».

## 3. Параметры ячейки (t, m, f, e, y, g, h) и вес фактора W

По документу (p. 3, 11): каждая ячейка-фактор в контексте пары характеризуется
семью нормализованными параметрами. Значения по умолчанию заданы в `factors.json`,
переопределяются калибровкой (§7).

| Параметр | Источник в паре |
|---|---|
| t | срочность: `urgency` сторон (норм.) |
| m | пространственная связанность фактора: 1.0 для location/format/commute, 0.2 для навыков |
| f | фактическая проверяемость: среднее (verified кандидата, clarity вакансии) |
| e | целевая релевантность: фактор входит в `career_trajectory` цель → 1.0 |
| y | критичность ущерба: must-have у вакансии или критично для кандидата → 0.9–1.0 |
| g | достоверность данных фактора (см. f; для самооценок E/F — 0.6 максимум) |
| h | ценность/ROI: вклад фактора в `motivation` кандидата и ценность для вакансии |

**Вес фактора (взвешенная формула состояния, p. 11):**

```
W_n = ( w_t·t + w_m·m + w_f·f + w_e·e + w_y·y + w_g·g + w_h·h ) · R_obj,n + ε_n
```

Глобальные веса параметров (калибруются, стартовые): `w_y=0.25, w_t=0.15, w_e=0.15,
w_h=0.15, w_f=0.10, w_g=0.10, w_m=0.10` (Σ=1.0).

- `R_obj,n ∈ [0.3, 1]` — ресурсная выполнимость: насколько разрыв по фактору закрыт
  ресурсами сторон (время на обучение, релокационный бюджет, гибкость графика). 1.0 —
  разрыва нет или он закрыт; ниже — закрытие сомнительно.
- `ε_n` — вклад энтропии фактора: неизвестное значение кандидата → ε_n = 0.15·w₀
  (вес фактора падает, скор не растёт из воздуха).

**Вклад фактора в скор пары:**

```
match_n = closeness(...)   — по типу фактора, §2.1
contribution_n = match_n · W_n
```

## 4. Φ-матрица (перекрёстные взаимодействия)

Правила в `data/phi_rules.json`. Формат:

```json
{
  "id": "PH-001",
  "comment": "СДВГ + гибкий график → синергия",
  "when": [
    {"factor": "neuro_profile", "op": "contains", "value": "adhd"},
    {"factor": "schedule", "op": "in", "value": ["flexible", "remote_friendly"]}
  ],
  "phi": 0.12,
  "scale_by": "min_weight"   // эффект умножается на min(W_a, W_b)
}
```

Семантика по документу (p. 6–7): `Φ>0` синергия, `Φ=0` нейтраль, `Φ<0` конфликт,
`Φ=−∞` (`"block": true`) — абсолютное противопоказание.

**Блокировки (Φ=−∞), обязательные:**
- must-have навык с уровнем < 80% требуемого или отсутствует;
- `work_format` вакансии не входит в допустимые кандидата;
- `schedule` не входит в допустимые (кроме случая, когда кандидат явно разрешил компромисс);
- зарплатные вилки не пересекаются и ни одна сторона не допускает торга;
- `work_permit`: нет права работать в требуемой юрисдикции;
- `location`: ЧП-окно удалёнки не пересекается (±3 ч) и релокация невозможна;
- must-have язык ниже требуемого уровня;
- **BL-008** абсолютное сенсорное противопоказание: чувствительность ≥ 0.8 × нагрузка среды ≥ 0.8 (медицински значимая перегрузка — запрет совместного назначения по документу, Φ=−∞).

**Конфликты (Φ<0), примеры:** сенсорная чувствительность × open-space; тревожность
(низкая стрессоустойчивость) × ночные смены; монозадачность × мультизадачная роль;
ценность стабильности × ранняя стадия стартапа.

**Синергии (Φ>0), примеры:** hyperfocus-профиль (СДВГ) × глубокая специализация;
гибкий график × уход за ребёнком; обучение за счёт компании × высокая обучаемость;
интересы-теги × теги продукта; менторство в вакансии × рост в менеджмент.

Итоговая сумма: `Σ Φ_jk = Σ (phi_rule · min(W_a, W_b))`, блокировка исключает пару целиком.

## 5. Модель ресурсов r

`r_n` — цена сближения пары по фактору (штраф в «Клее»). Таблица стартовых стоимостей:

| Разрыв | r |
|---|---|
| Релокация без пакета | 0.80 |
| Релокация с пакетом | 0.35 |
| Обучение must-have навыку (если сторона допускает) | 0.5 · (1 − learnability) |
| Обучение nice-to-have | 0.15 |
| Компромисс по графику/формату (кандидат терпит) | 0.30 |
| Зарплатный компромисс (пересечение < 50% вилки) | 0.25 |
| Коммутирование сверх max | 0.2 · перерасход (log) |
| Онбординг джуна на сеньорской задаче (мismatch опыта) | 0.40 |

## 6. Скор пары (КЛЕЙ) и энтропия ε

По документу (p. 6): `КЛЕЙ_итоговый = Σ W_i − Σ r_i + Σ Φ_jk − ε`.

Реализация (все слагаемые ≥ 0, кроме Φ):

```
RAW = Σ_n (match_n · W_n) − Σ_n r_n·gap_n + Σ_rules (phi · min(W_a, W_b)) − ε_total
SCORE = RAW / Σ_n W_n          — нормировка к 0..1 (агрегация для сортировки,
                                 вектор факторов сохраняется для «распаковки», p. 9)
```

`ε_total = clamp(0.5·missing_канд + 0.3·missing_вак + 0.2·только_самоотчёты, 0, 0.35)`

Пороги выдачи: SCORE ≥ 0.75 «сильный матч», 0.55–0.75 «достойный», 0.40–0.55
«условный (есть что сближать)», < 0.40 не показывается; блокировки — отдельная ветка
«невозможно, потому что …».

## 7. Калибровка весов

1. Берутся 5 тест-кейсов (§9) с эталонным порядком.
2. `tests/test_calibration.py` проверяет: эталонный топ-1 воспроизводится,
   порядок в пределах кейса сохраняется, SCORE(топ-1) ≥ 0.70 у «сильных» кейсов.
3. Подбор w (глобальных и факторных w₀) — жадный по кейсам, изменения фиксируются
   в `data/calibration.json` с указанием, какой кейс и почему двигали.
4. Весам запрещено меняться в рантайме бота; только через версию конфига (индекс доверия
   и итеративный цикл меняют W в контексте пары, но не глобальные веса).

## 8. Итеративный цикл (i → i+1) и индекс доверия

Событие фидбека (по документу p. 11–12: «выполнил микро-метод + обратная связь»):

| Событие | Эффект |
|---|---|
| Кандидат: дислайк «не мой формат» | w₀(work_format, schedule) профиля +20% (cap 1.0) |
| Кандидат: дислайк «не та сфера» | w₀(domain_experience, interests) +20% |
| Отклик без ответа 14 дней | trust_index вакансии −0.1, ε вакансии +0.02 |
| Отказ по навыку | W(hard_skills) в парах с этим кандидатом +15%; зона валентности указывает навык |
| Успешный контакт (интервью) | trust_index вакансии +0.1, w₀ затронутых факторов −5% (уже сошлось) |

Условие остановки по паре (p. 9): 3 итерации без изменения SCORE > 0.02 → пара
замораживается (не перевыдвигается). Индекс доверия вакансии/кандидата: старт 0.7,
clamp [0.2, 1.0], умножает R_obj.

## 10. Схема БД (SQLite → PostgreSQL-совместимая)

```sql
users(id INTEGER PK, tg_id INTEGER UNIQUE NOT NULL, role TEXT CHECK(role IN ('candidate','employer','admin')),
      created_at TEXT DEFAULT (datetime('now')));

candidate_profiles(user_id INTEGER PK REFERENCES users(id),
      data_json TEXT NOT NULL,        -- сырой анкетный ввод
      norm_json TEXT NOT NULL,        -- нормализованный профиль 0..1
      completeness REAL DEFAULT 0,    -- доля заполненных факторов
      sensitive_consent INTEGER DEFAULT 0,
      weights_json TEXT,              -- персональные калибровки w₀ после фидбека
      updated_at TEXT);

employers(user_id INTEGER PK REFERENCES users(id),
      company_json TEXT NOT NULL, verified INTEGER DEFAULT 0, trust_index REAL DEFAULT 0.7);

vacancies(id INTEGER PK, employer_id INTEGER REFERENCES employers(user_id),
      data_json TEXT NOT NULL, norm_json TEXT NOT NULL,
      status TEXT CHECK(status IN ('draft','active','paused','closed')) DEFAULT 'draft',
      trust_index REAL DEFAULT 0.7,
      moderation TEXT DEFAULT 'pending',   -- автопроверка формулировок
      created_at TEXT);

matches(candidate_id INTEGER REFERENCES candidate_profiles(user_id),
      vacancy_id INTEGER REFERENCES vacancies(id),
      score REAL, band TEXT, breakdown_json TEXT,   -- вклад факторов + Φ + r + ε
      blocked INTEGER DEFAULT 0, block_reasons_json TEXT,
      iterations INTEGER DEFAULT 0, frozen INTEGER DEFAULT 0,
      computed_at TEXT, PRIMARY KEY(candidate_id, vacancy_id));

feedback_events(id INTEGER PK, user_id INTEGER REFERENCES users(id),
      match_candidate_id INTEGER, match_vacancy_id INTEGER,
      kind TEXT, payload_json TEXT, created_at TEXT);

factor_config(version INTEGER PK, created_at TEXT,
      factors_json TEXT, phi_json TEXT, param_weights_json TEXT, calibration_json TEXT);
seed(version INTEGER PK, applied_at TEXT);
```

«Распаковка» (p. 9): breakdown_json хранит вектор вкладов — для объяснимости и зоны
валентности, скаляр SCORE используется только для сортировки.

## 11. Зона валентности (алгоритм первопричины)

По документу (p. 9–10): первопричина = узел, чьё «обнуление» (интервенция) даёт
максимальное снижение общего ущерба. Для кандидата с потоком слабых матчей:

1. Собираем вектор ущерба: `loss_n = (1 − match_n) · W_n + r_n·gap_n − Φ⁺_n`.
2. Для каждого фактора считаем гипотетический `SCORE` при `match_n := 1` (полное
   закрытие разрыва) — «выигрыш от интервенции».
3. Первопричина = фактор с максимальным выигрышем, при близких (< 10% разницы) —
   предпочтение меньшему `r` (детерминированный тай-брейк по документу, p. 12).
4. Формулировка ответа `/why`: топ-3 фактора-причины + конкретное действие
